# 0009: Backup with restic

## Context
Sync copies deletions and edits, so it is not a backup: the 30-day local versions and the Drive trash are not a history the user controls. The owner wants periodic, versioned, encrypted backups of any list of folders, to a Drive account or a disk, that can be restored on another machine. The only transport syncfast has is rclone.

## Decision
- **Engine.** restic, bundled in the Flatpak next to rclone as the official release binary (`restic_<version>_linux_<arch>.bz2`, a single bzip2-compressed executable, pinned version and sha256 per architecture, bumped with `just pin-restic`). It reaches Drive through `rclone:<account>:<path>` with the bundled rclone, so the accounts of Settings > Accounts are reused and there is no second credential store. A local absolute path (external disk) also works. The release signature is not verified: the pinned sha256 is the whole check, and a person updates it in a PR that shows the version, the URLs and the hashes.
- **Why restic.** Its machine-readable contract is documented per command (`--json` for `backup`, `snapshots`, `ls`, `check`, `restore`; exit codes 3, 10, 11, 12) and was verified against fixtures, the same way rclone's bisync log is (ADR 0005); its repository is encrypted, deduplicated and versioned by design; and `rclone` is a first-class backend. kopia has comparable features and an rclone provider, but it was not evaluated beyond its docs and its extra server mode is not needed here. rclone alone (`copy`/`sync` with `--backup-dir`) has no encryption or deduplication and no snapshot or retention model, and a point-in-time restore would mean managing dated folders by hand.
- **Key.** syncfast generates the repository password: 32 random bytes in base32 (52 characters, shown in groups of four). It is handed to restic on stdin (`--password-file /dev/stdin`), never in argv, the environment or a file. It is shown once with a mandatory `I Saved the Key` step, can be shown again behind a confirmation, is never logged and is never returned by `ops`. Restoring on another machine means typing it; syncfast cannot recover it.
- **Key storage**, with the `oo7` crate, in this order:
  1. The XDG Secret portal (`org.freedesktop.portal.Secret`). Inside the sandbox the keyring is an encrypted file keyed by the portal's per-app secret, which other apps cannot read. This is the preferred store.
  2. When the portal is missing (its frontend does not expose the interface, error `PortalNotFound`), the host Secret Service (`org.freedesktop.secrets`), through `--talk-name=org.freedesktop.secrets` in the Flatpak `finish-args`. Any other portal error does not fall through: the key is not silently put somewhere the user did not expect.
  3. Neither available: no backup can be created, and the app says why.

  The cost of step 2: that talk-name lets the sandbox reach every secret in the host keyring, not only syncfast's. `oo7` itself advises sandboxed apps to prefer the portal for that reason. The cost is bounded, not new: the app already holds `org.freedesktop.Flatpak` (ADR 0006), which runs any host command. The portal stays preferred, and Settings > Backups shows which store is in use and warns on the host keyring. `oo7` 0.6.0 does not fall back to the host when the portal is missing (its `Keyring::new()` returns the portal error); 0.7.0-beta does, and `Oo7KeyStore` writes the order itself so the active store is known.
- **Destination.** One repository per backup of a config, outside the local and remote folder of every sync, outside every folder being backed up (local destinations), never shared or nested with another backup of the same config, empty when created, and reachable from the sandbox. The destination is fixed after creation; a different one is a new backup. Another machine may open the same repository with its own backup entry.
- **Host and retention.** Snapshots use the machine's real hostname (`--host <hostname>`, restic's own default), not a fixed name, so two machines can back up to one repository. `forget` runs with `--host <hostname> --group-by host`: a machine prunes only its own snapshots, and all of them form one group whatever the list of folders, so snapshots of an older folder list age out under the same policy instead of staying forever. After a hostname change, the old snapshots look like another machine's (listed, never deleted) and the first run rereads everything, with little upload because restic deduplicates. Restoring on a new machine is typing the key.
- **Retention.** `keep` has `daily`, `weekly`, `monthly` and `yearly`; `yearly` is optional and 0 (off) by default. restic's `last` and `hourly` are not offered.
- **Filters.** Backups reuse the sync filter presets, with a new preset `build_artifacts` (`node_modules/`, `target/`, `.venv/`, `venv/`, `__pycache__/`, `.gradle/`, `.cache/` and a few tool caches: things a tool rebuilds, never `.git`). It is on by default for new backups and opt-in for syncs. `build/`, `dist/`, `out/`, `bin/` and `obj/` are left out on purpose: `build/` is also a common name for real content, and excluding it by mistake loses data that no command recreates. `dev_dirs` (which leaves out `.git`) is not a backup default.
- **Bandwidth and file systems.** `limit_upload` and `limit_download` per backup (the phase 2 speed type, `off` by default) become restic's `--limit-upload` and `--limit-download` in KiB/s. `one_file_system` per backup, `true` by default: mounts and Btrfs subvolumes inside a folder are not crossed; turning it off includes them, and everything mounted inside the folders with them.
- **Safety without a review.** A backup never deletes user files, so the review levels of ADR 0002 do not apply. In their place: a missing or empty source never produces a snapshot (restic would exit 3 and save a partial one); retention (`forget --prune`) runs only after a successful non-empty backup, and lowering `keep` asks for confirmation; a check that finds errors sets `needs_attention` with fault `repo_damaged`, which holds backups and cleanup until a full check passes. Stale repository locks are removed with `unlock` (never `--remove-all`) and the command is retried once.
- **Integrity.** A sample check (`check --read-data-subset=5%`) every month, and after a series of failed backups a structural `check` without `--read-data` (indexes, trees and snapshots, no pack reads), because reading all data after every failure would download the whole repository from Drive. Repair is not automated and is left to a future phase.
- **Schedule.** Per backup, `syncfast-backup_<id>.service` and `.timer` (`_` cannot occur in a sync id, so the names never collide). Daily at 03:00 with `Persistent=true` by default; the service exits 75 when the network or the destination is missing and `Restart=on-failure` tries again in 15 minutes. The units keep `Nice=15` and `IOSchedulingClass=idle`.
- **Agents (extends ADR 0007).** An agent can list backups and snapshots, read names, sizes and dates inside a snapshot, run a backup or a check now, pause and resume, create a backup, edit it, and restore into a folder that does not exist yet, never in place. Edits go through the phase 2 `lowers_safety` guard, extended to backups: only the user can lower a `keep` value, remove a backup, remove a source folder, change the destination or turn `one_file_system` off (exit 4, nothing written). The key is never exposed to an agent. A backup created by an agent generates and stores its key inside the process and runs at once; the GUI shows a `Save the backup key` notice, and a notification, until the user completes `I Saved the Key`. That flag does not hold the backup.

## Consequences
- Losing the key loses the backup. The UI says so where the key is shown, and says it again for a backup an agent created.
- Creating a backup needs a Secret portal or a host Secret Service. A desktop with neither cannot create backups, and the app says why. On this machine's Hyprland setup the portal has no Secret backend until `org.freedesktop.impl.portal.Secret=gnome-keyring` is added to the portal config; until then the host keyring is used.
- With the host keyring, the sandbox can read every secret in it. The portal is safer and stays preferred.
- `oo7` adds `zbus` and `ashpd` to the core; `boundary.rs` still holds because none is a UI crate. The core pins `oo7 =0.7.0-beta`: the stable 0.7.0 needs `zbus` 6, which would put a second `zbus` next to the one `fastframe` and `ashpd` use, while the beta resolves to a single `zbus` 5.19.0 and passes `cargo deny check`. Moving to the stable release is a change of this line once the rest of the tree moves to `zbus` 6.
- The rclone backend runs `serve restic --stdio --drive-use-trash=false`, so packs removed by `prune` leave Drive for good instead of staying in the trash and in the quota. This still needs a check against a real Drive.
- Two machines can write to one repository. A `prune` takes an exclusive lock, so the other machine's backup can fail with exit 11 and tries again on its next run; restic never treats another host's lock as stale before 30 minutes.
- A changed list of folders or a renamed machine leaves snapshots that no retention run removes (see Host and retention).
- An agent that creates a backup leaves the user a task (saving the key) the user may not notice for a while; the notice and the notification are the only reminder.
- A restic upgrade can change JSON fields or messages; the fixtures in `tests/fixtures/restic-<version>/` and `just capture-restic-fixtures` catch that.
