# 0009: Backup with restic

## Context
Sync copies deletions and edits, so it is not a backup: the 30-day local versions and the Drive trash are not a history the user controls. The owner wants periodic, versioned, encrypted backups of any list of folders, to a Drive account or a disk, that can be restored on another machine. The only transport syncfast has is rclone.

## Decision
- **Engine.** restic, bundled in the Flatpak next to rclone as the official release binary (`restic_<version>_linux_<arch>.bz2`, a single bzip2-compressed executable, pinned version and sha256 per architecture, bumped with `just pin-restic`). It reaches Drive through `rclone:<account>:<path>` with the bundled rclone, so the accounts of Settings > Accounts are reused and there is no second credential store. A local absolute path (external disk) also works.
- **Why restic.** Its machine-readable contract is documented per command (`--json` for `backup`, `snapshots`, `ls`, `check`, `restore`; exit codes 3, 10, 11, 12) and was verified against fixtures, the same way rclone's bisync log is (ADR 0005); its repository is encrypted, deduplicated and versioned by design; and `rclone` is a first-class backend. kopia has comparable features and an rclone provider, but it was not evaluated beyond its docs and its extra server mode is not needed here. rclone alone (`copy`/`sync` with `--backup-dir`) has no encryption or deduplication and no snapshot or retention model, and a point-in-time restore would mean managing dated folders by hand.
- **Key.** syncfast generates the repository password: 32 random bytes in base32 (52 characters, shown in groups of four). It is handed to restic on stdin (`--password-file /dev/stdin`), never in argv, the environment or a file, and stored with the `oo7` crate in the keyring through the XDG Secret portal (inside the sandbox, an encrypted file keyed by the portal's per-app secret). It is shown once with a mandatory `I Saved the Key` step, can be shown again behind a confirmation, is never logged and is never returned by `ops`. Restoring on another machine means typing it; syncfast cannot recover it.
- **Destination.** One repository per backup, outside the local and remote folder of every sync, outside every folder being backed up (local destinations), never shared or nested with another backup's, empty when created, and reachable from the sandbox. The destination is fixed after creation; a different one is a new backup.
- **Safety without a review.** A backup never deletes user files, so the review levels of ADR 0002 do not apply. In their place: a missing or empty source never produces a snapshot (restic would exit 3 and save a partial one); retention (`forget --prune`) runs only after a successful non-empty backup, and lowering `keep` asks for confirmation; a check that finds errors sets `needs_attention` with fault `repo_damaged`, which holds backups and cleanup until a full check passes. Stale repository locks are removed with `unlock` (never `--remove-all`) and the command is retried once.
- **Schedule.** Per backup, `syncfast-backup_<id>.service` and `.timer` (`_` cannot occur in a sync id, so the names never collide). Daily at 03:00 with `Persistent=true` by default; the service exits 75 when the network or the destination is missing and `Restart=on-failure` tries again in 15 minutes.
- **Agents (extends ADR 0007).** An agent can list backups and snapshots, read names, sizes and dates inside a snapshot, run a backup or a check now, pause and resume, and restore into a folder that does not exist yet, never in place. It cannot create, remove or edit a backup or touch the key: creating shows the key to the user, and the folders, filters, retention and destination can hide or delete history.

## Consequences
- Losing the key loses the backup. The UI says so where the key is shown.
- Creating a backup needs a Secret portal backend. A desktop without one (this machine's Hyprland setup, until `portals.conf` routes `org.freedesktop.impl.portal.Secret` to gnome-keyring) cannot create backups, and the app says why.
- `oo7` adds `zbus` and `ashpd` to the core; `boundary.rs` still holds because none is a UI crate.
- The rclone backend runs `serve restic --stdio --drive-use-trash=false`, so packs removed by `prune` leave Drive for good instead of staying in the trash and in the quota. This still needs a check against a real Drive.
- Two machines writing to the same repository are not supported.
- A restic upgrade can change JSON fields or messages; the fixtures in `tests/fixtures/restic-<version>/` and `just capture-restic-fixtures` catch that.
