# 0002: Bisync safety invariants

## Context
`rclone bisync` can delete or overwrite data on both sides. A wrong flag or an unreviewed resync can destroy a Drive folder or a local tree.

## Decision
- The bisync arguments are fixed and built in one place (`bisync_args`), driven by the `Behavior` resolved for each sync from the built-in defaults, `[defaults]` and the sync's own keys. Local is always Path1, remote Path2.
- Review gates the pair: the first run, a changed filter set, a changed mode, a non-recoverable critical error, `--max-delete` overruns and rclone's "all files were changed" safety abort. A gated pair runs again only after a dry-run preview and a confirmation, by the user or, at the levels below, by syncfast. `--resync` and `--force` are never used without that confirmation marker.
- The `review` setting has three levels, default `deletions`. `manual`: every gate waits for the user. `deletions`: syncfast writes the confirmation marker itself when the gate's dry run deletes nothing on either side (`delete_local == 0 && delete_remote == 0`, the same test that lets an agent confirm). `automatic`: it also confirms deletions, and the GUI warns. It applies to the gates `needs_review_first_run`, `needs_review_filters_changed`, `needs_review_mode_changed`, `all_files_changed` and `too_many_deletes`, once per gate and level (`Gate.auto_checked`), and the round records `auto_reviewed` for Activity.
- The first run of a sync is the exception: it waits for the user at `manual` and at `deletions`, even when its dry run deletes nothing, because a wrong pairing merges two folders without deleting anything and that choice happens once per sync. Only `automatic` confirms a first run on its own.
- Floor, whatever the level: `needs_review_critical_error` is never confirmed by syncfast, and an empty source (`Fault::LocalEmpty` for bisync, the equivalent check before a one-way run) is a `needs_attention` gate that no review can release.
- Lowering a safety setting is a user action (ADR 0007): CLI and MCP refuse `review` below the current level, a higher `max_delete`, `versions = false`, `conflict_loser = delete` and a switch to a mirror mode (exit 4, `This setting lowers safety (<keys>). Change it in syncfast.`). The GUI writes the config directly.
- A sync mode other than `bisync` runs `rclone copy` or `rclone sync` behind the same gates (ADR 0008).
- `--exclude-if-present` is never used: `git init` in an already synced folder would make bisync delete it on Drive. `.git/` is excluded by a filter preset instead. The `git_repos` preset is the safe way to leave out whole repositories: syncfast scans the local tree and renders one anchored rule per repo into the filters file, so a new repo changes `filters_hash` and goes through review.
- `git_repos` is on by default: a pair without a `presets` key gets it, and the first repo found in the local tree sends that sync to the filters-changed review.
- Anything deleted or overwritten on the local side goes to `$XDG_DATA_HOME/syncfast/versions/<id>/` through `--backup-dir1`, in one dated folder per run (`<AAAAMMDD-HHMMSS>/`), and is pruned after `versions_keep_days` (30 by default) by the folder's name. `versions = false` drops `--backup-dir1`. No `--suffix` is used: it would rename the old remote copy beside the file and sync it back as a new file. The remote side relies on the Drive trash and revisions. The one-way modes follow the same rule (ADR 0008).
- A confirmed marker survives a `Transient` or `NeedsAttention` failure and stays valid while its `filters_hash` matches; any other outcome that sets a gate deletes it. A never-synced pair whose confirmed first run failed as `NeedsAttention` runs that resync again instead of going back to its first review.
- A pending gate is never replaced by `local_missing`: the review survives the folder going away and coming back. `config_error` ends by itself once the pair is valid again (a pair that never synced goes back to its first review). Removing an account clears `applied_filters_hash` and the marker of its syncs, so an account created later under the same name starts them with that review.
- The "all files were changed" abort (every file of a side changed at once, typical of a one-file folder) is cleared like a mass deletion: a `--force` round after a confirmed preview.
- A normal round that fails with `Empty prior Path1 listing` or `Empty prior Path2 listing` (the pair was empty on both sides at its last sync, so rclone keeps empty listings and refuses to continue) is retried once in the same `run` as a `--resync`. It needs no review: a resync only copies, and an empty prior listing leaves no known deletion to propagate.
- Renames are moves: normal, forced and forced dry-run rounds pass `--track-renames --track-renames-strategy hash,modtime --max-delete-renames-aware`, and the mirrors pass `--track-renames --track-renames-strategy hash,modtime` to `rclone sync`. A renamed folder no longer counts as deleting every file in it, so it does not trip `--max-delete`. A resync leaves the flags out (it only copies). `--slow-hash-sync-only` is never passed: rclone rejects it next to a hash strategy.
- A failure is judged by the log of the run that just ended. Listings count as lost only when some `X.lst-err` has no `X.lst` beside it (rclone renamed it in this run); a stale `.lst-err` next to a valid listing is ignored. A subfolder that vanished while rclone listed it (`error reading source directory` or `error reading destination directory` on a named object) is `Transient`: the next round lists the new state.
- A local folder emptied behind the pair's back (an unmounted drive) deletes nothing on the remote: rclone refuses an empty current listing (`Empty current Path1 listing`, exit 7), and that is `Fault::LocalEmpty`, a `needs_attention` gate at once. Covered by `an_emptied_local_folder_needs_attention_at_once_and_the_remote_keeps_every_file`.
- A failure the user can fix (account, quota, permission, missing remote folder, or transient failures lasting over 6 hours) sets `needs_attention`, the one gate that does not stop rounds. A `state.json` that is not valid JSON is set aside as `state.json.corrupt-<stamp>` and the pair goes back to its first review. A bisync workdir that cannot be read (other than being absent) counts as lost listings.
- Google Docs are skipped (`--drive-skip-gdocs`). It is not a setting: the phase 2 spike rejected an `export` or `url` key (ADR 0010).

## Consequences
- Some rounds stop and wait for the user; the UI and tray say so.
- The preview comes from `--dry-run`, which may list deletions the real run would not do. The UI says that.
- Every `Behavior` field is a config key (`[defaults]` and per-sync overrides), so the engine takes its values from the resolved `Behavior` and never from a literal.
- A mass deletion or a first review that is confirmed on its own can still delete files at `automatic`. The GUI says so, and `lowered_safety` lists every setting below the built-in default so a change made outside the GUI stays visible.
